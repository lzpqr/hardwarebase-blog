硬件产品几乎不存在“一次设计就完美”的情况。

样机测试会暴露问题，量产会暴露良率，客户使用会暴露边界场景，供应链会带来停产和涨价，认证会提出整改要求。产品竞争力很大程度上取决于团队发现问题、判断问题、闭环问题和沉淀经验的能力。

迭代不等于“改板”，更不等于“哪里出问题就改哪里”。没有根因分析的迭代，只是把问题从一个版本搬到另一个版本；没有影响评估的迭代，可能在解决一个问题的同时引入三个新问题；没有验证策略的迭代，会让版本差异变成无法追溯的风险。

> 本文是硬件开发流程系列的第八篇。建议先阅读 [调试与验证篇](/posts/hardware-development-debugging-validation/) 和 [PCB 制板与贴片篇](/posts/hardware-development-pcb-fabrication-assembly/)。

## 理解迭代：类型、目标与边界

### 常见迭代类型

| 类型 | 典型触发 | 核心目标 |
| --- | --- | --- |
| 问题整改 | 测试失效、客户投诉 | 消除缺陷，恢复可用性 |
| 性能优化 | 指标不达标或裕量不足 | 提升性能和可靠性 |
| 降本迭代 | 成本压力、竞品压力 | 在保证底线前提下降低成本 |
| 器件替换 | 停产、缺货、涨价、国产化 | 保障供应并控制风险 |
| 认证整改 | EMC、安规、无线认证 | 满足合规要求 |
| 量产改进 | 良率低、工艺不稳定 | 提升良率和一致性 |
| 功能升级 | 市场需求、客户定制 | 增加或调整产品能力 |
| 平台化演进 | 产品系列扩展 | 提高复用和迭代效率 |

不同类型迭代的评估重点不同。问题整改以闭环为先，降本和器件替换以风险控制为先，功能升级以需求管理为先。

### 迭代要回答的五个问题

1. 为什么要改？
2. 改什么？
3. 怎么改？
4. 改完怎么验证？
5. 改动影响谁？

触发原因必须真实、充分、可量化；变更范围必须明确；方案必须经过比较；验证方法和判定标准必须清楚；还要评估对软件、结构、认证、库存、客户和售后的影响。

### 三层目标

| 层次 | 目标 | 典型表现 |
| --- | --- | --- |
| 问题闭环 | 消除已发现的缺陷 | 根因明确、措施有效、复测通过 |
| 性能提升 | 改善指标、裕量和可靠性 | 达标并有裕量、批产稳定 |
| 产品延续 | 保障供应、成本和生命周期 | 可持续生产、可维护、可升级 |

只解决眼前问题、不考虑产品延续的迭代，可能在未来引发新的停产或认证风险。

### 版本管理

- 明确主版本、次版本和修订版本规则；
- 明确哪些变更需要升版本；
- 每个版本对应原理图、PCB、BOM、软件、工艺和测试文件；
- 样机、库存和出货产品可追溯到具体版本；
- 版本发布必须有评审记录和放行结论。

## 1. 迭代的触发与决策

### 触发来源

- 测试发现：功能、性能、环境、EMC 或安规测试不通过；
- 量产反馈：良率下降、工艺漂移或来料异常；
- 客户反馈：现场故障、兼容性或使用体验问题；
- 售后数据：返修率、失效模式和批次差异；
- 供应链信息：停产、交期延长或价格上涨；
- 成本压力：BOM 或制造成本高于目标；
- 认证要求：标准更新或整改；
- 市场需求：功能升级、竞品对标或定制需求。

### 必要性评估

并不是每个问题都需要改板。

需要评估：

- 问题的严重程度和发生概率；
- 是否能通过软件、工艺或说明规避；
- 是否存在临时措施和长期措施；
- 不改的后果和修改的代价；
- 是否影响认证、结构或兼容性；
- 应当立即改、下个版本改，还是随换代处理。

### 优先级分级

| 级别 | 判定 | 处理方式 |
| --- | --- | --- |
| 紧急 | 安全、批量失效、无法出货 | 立即处理并快速评审 |
| 高 | 影响主要功能或认证 | 纳入近期版本，专项跟踪 |
| 中 | 影响性能、体验或成本 | 纳入计划迭代 |
| 低 | 优化项、非阻塞问题 | 合并到后续版本或换代考虑 |

### 决策流程

1. 收集问题与数据；
2. 分析根因和影响范围；
3. 制定候选方案并比较；
4. 评估成本、交期、风险和收益；
5. 评审并做决策；
6. 明确责任人和时间节点；
7. 执行、验证并闭环。

改动涉及已投产板卡和物料时，需要评估报废和在制品处理，并提前设计新旧版本共存方案。不要为了赶交期跳过必要验证。

## 2. 问题闭环与根因分析

### 问题分类

- 按类别：电源、时钟、接口、模拟、结构、工艺、软件、物料；
- 按阶段：设计、工艺、来料、使用；
- 按影响：安全、功能、性能、体验、成本；
- 按性质：偶发、必现、批次性、系统性。

### 根因分析方法

| 方法 | 适用场景 |
| --- | --- |
| 5Why | 单点问题，逐层追问原因 |
| 鱼骨图 | 多因素问题，头脑风暴整理 |
| 故障树 | 复杂系统，从现象逐层分解 |
| 8D | 客户投诉和批量问题 |
| DOE | 工艺参数优化和多因素分析 |
| 对比试验 | 新旧版本或多方案对比 |

要区分：

- 直接原因：导致现象的直接因素；
- 根本原因：导致直接原因出现的深层因素；
- 系统性原因：导致问题没有被提前发现的管理或流程因素。

只解决直接原因，问题会重复；解决系统性原因，才能防止复发。

### 纠正、预防与沉淀

纠正措施针对已发生的问题，预防措施针对同类问题再次发生。措施必须具体、可执行、可验证，并有责任人和完成时间。

问题库应记录现象、根因、措施和验证结果，并将典型问题转化为设计规范和检查清单。

## 3. 变更管理（ECN/ECO）

### 变更类型

- 设计变更：原理图、PCB、结构和软件；
- 物料变更：型号、品牌、规格和替代料；
- 工艺变更：板厂工艺、贴片参数和材料；
- 文件变更：图纸、规范和测试标准；
- 软件变更：固件、驱动和配置。

### 变更流程

1. 提出变更申请，说明原因和范围；
2. 相关角色评估影响；
3. 制定变更方案和验证计划；
4. 评审并批准；
5. 执行变更并更新文件；
6. 验证并放行；
7. 记录并归档。

变更申请人、评估人、批准人和执行人应适当分离，避免“自己改、自己批”。

### 影响评估

| 维度 | 评估内容 |
| --- | --- |
| 电气 | 参数、时序、裕量、EMC 和安规 |
| 结构 | 尺寸、装配、散热和外观 |
| 软件 | 引脚、寄存器、协议和版本兼容 |
| 认证 | 是否需要重新测试或认证 |
| 成本 | 物料、工艺、测试和认证费用 |
| 库存 | 成品、半成品和在途物料处理 |
| 客户 | 兼容性、切换方式和通知要求 |
| 售后 | 备件、维修和技术支持 |

变更验证范围由影响评估决定，必须同时验证变更项和受影响关联项。关键变更要重新做首件和小批试产。

## 4. 迭代的输入与准备

### 输入清单

- 问题清单和根因分析报告；
- 测试数据、失效样品和现场反馈；
- 物料供应和价格信息；
- 成本目标和竞品信息；
- 认证和法规变化；
- 结构、软件和工艺约束。

### 范围与风险

明确本次“改什么、不改什么”，明确必须闭环和可以延后的问题。

风险包括：

- 技术风险：方案可行性、参数裕量和验证难度；
- 供应风险：交期和替代料认证；
- 进度风险：验证、认证和客户交期；
- 成本风险：改板、报废和测试费用；
- 兼容风险：软件、结构和客户系统影响。

### 计划与里程碑

明确方案评审、设计完成、样机、验证、试产和量产节点，并为异常处理和返工预留时间。

## 5. 设计修改的常见方向

### 电路和器件

- 增加降额裕量；
- 优化保护电路；
- 调整滤波和去耦；
- 更换供货稳定、成本更优或性能更好的器件；
- 增加测试点和调试手段。

### PCB

- 缩短关键回路和电源路径；
- 优化布线和参考平面；
- 调整叠层和阻抗；
- 优化散热铜皮和过孔；
- 改善拼板、焊盘和可制造性。

### 结构、软件和工艺

结构修改包括安装方式、限高、连接器、散热、结构强度和防护。

软件要保证引脚、寄存器和配置与硬件版本同步，并可增加异常检测和容错机制。

工艺修改包括钢网、回流曲线、贴装参数、板厂工艺、测试工装和包装运输。

## 6. 降本设计迭代

### 降本方向

- 器件替代；
- 方案优化，减少器件数量；
- PCB 层数、面积、工艺和拼板优化；
- 结构材料和装配简化；
- 工艺优化，减少特殊工艺；
- 合并料号，规模化采购。

### 不能牺牲的底线

- 安全和认证要求；
- 关键参数裕量和可靠性；
- 环境适应性和寿命；
- 可测试性和可维护性；
- 客户明确要求和合同条款。

降本后必须验证替代器件、试产良率和长期供货稳定性，并保留原设计作为风险备份。

## 7. 国产替代与器件替换

### 替换评估维度

| 维度 | 关注点 |
| --- | --- |
| 电气参数 | 电压、电流、精度、带宽和功耗 |
| 封装引脚 | 尺寸、间距、引脚定义和散热焊盘 |
| 软件兼容 | 寄存器、驱动、协议和配置 |
| 温度等级 | 工作温度、参数漂移和降额 |
| 质量认证 | 可靠性数据、认证状态和失效率 |
| 供货能力 | 产能、交期、生命周期和价格 |
| 技术支持 | 原厂支持、参考设计和问题响应 |

### 替换流程

1. 参数对比和风险评估；
2. 样机替换和功能验证；
3. 关键指标和边界测试；
4. 环境和可靠性验证；
5. 小批试产；
6. 认证影响评估；
7. 放行并建立双源。

常见风险包括参数“看似相同”但关键指标差异明显、封装兼容但散热工艺不同、寄存器兼容但时序不同，以及替换后供货能力并没有真正改善。

关键器件建立第二货源时，两个来源都必须分别验证并纳入 BOM。## 8. 认证与合规迭代

### 认证整改

- 明确不通过项和测试条件；
- 分析是设计、工艺还是测试布置问题；
- 制定整改方案并做预测试；
- 整改后复测并保留数据；
- 必要时重新提交认证。

### 变更对认证的影响

- 涉及射频、电源、安规、结构或关键器件的变更，通常需要重新评估；
- 判断是否需要重新测试、部分测试或备案；
- 保留变更前后的差异说明和测试证据；
- 与认证机构提前沟通，避免重复劳动。

如果无法确认影响，应按更严格的方式处理。重新认证的成本和时间必须纳入迭代计划。

## 9. 迭代验证策略

### 差异验证与回归验证

- 差异验证针对变更项本身；
- 回归验证针对受影响的关联功能和接口；
- 变更越靠近底层，回归范围越大；
- 关键安全、认证和量产项必须重新验证。

### 验证范围

验证范围由以下因素决定：

- 变更类型和位置；
- 对电气、结构、软件和工艺的影响；
- 产品当前处于样机、试产还是量产阶段；
- 客户和认证的强制要求；
- 历史问题的复发风险。

### 对比验证

- 新旧版本在相同条件下对比测试；
- 对比关键指标、波形、温升和功耗；
- 记录差异并分析原因；
- 对比验证能快速发现“改一处、动一片”的隐性影响。

### 小批试产与放行

小批试产应使用正式工艺和物料，验证良率、一致性和测试覆盖，确认可以稳定量产后再全面切换。

放行前确认：

- 所有变更项和关联项验证完成；
- 关键指标满足判定标准；
- 遗留问题已评估并有处理计划；
- 文件、物料和软件版本一致；
- 由授权人签字放行。

## 10. 版本管理与文档同步

### 版本命名与标识

- 版本号规则清晰，避免“最终版”“最终版2”；
- 硬件、软件、结构和工艺版本分别标识；
- 样机和成品有明确的版本标识和追溯方式。

### 文件一致性

一次迭代通常涉及：

- 原理图、PCB、BOM 和装配图；
- 结构图纸和物料清单；
- 软件版本和配置说明；
- 工艺文件、钢网和测试程序；
- 验证报告、认证资料和使用说明。

这些文件必须同步更新。

### 变更记录与留样

每个版本都要有完整变更记录，包含原因、内容、影响、验证和责任人。

样机标注版本、日期和编号，保留关键版本样机和测试数据，用于对比分析、失效复现和售后参考。

## 11. 库存、在制品与客户影响

### 库存处理

- 清查成品、半成品、在途物料和原材料；
- 评估继续使用、返工、降级或报废；
- 计算库存处理的成本和交期影响；
- 明确新旧版本切换节点。

### 新旧版本共存

明确两个版本的差异和兼容性，建立版本识别机制，避免新旧混用在同一系统或同一批次。

### 客户通知与售后

- 评估变更对客户的影响和兼容性；
- 按合同和流程提前通知客户；
- 提供切换计划、验证数据和技术支持；
- 备件版本与出货版本对应；
- 对停产版本保留维修方案；
- 将现场问题反馈到下一轮迭代。

## 12. 跨部门协同与迭代效率

### 角色与职责

| 角色 | 职责 |
| --- | --- |
| 产品/项目经理 | 需求、优先级、进度和决策 |
| 硬件工程师 | 方案、设计、验证和问题分析 |
| 软件工程师 | 驱动、固件、兼容性和联调 |
| 结构工程师 | 结构、散热和装配影响 |
| 工艺/制造 | 可制造性、工艺和试产 |
| 测试工程师 | 验证方案、测试执行和数据 |
| 采购/供应链 | 物料、交期、价格和替代 |
| 质量工程师 | 流程、闭环、放行和追溯 |
| 认证工程师 | 认证影响和合规 |

### 沟通和升级

建立统一问题清单和状态跟踪，定期召开迭代评审和风险会议，关键决策留痕。对影响安全、认证和客户的问题优先处理。

### 迭代节奏与平台化

- 明确迭代目标，避免范围无边界扩张；
- 把大改动拆分为可验证的小步骤；
- 关键路径提前启动，长交期物料提前准备；
- 通过平台化和模块化提高复用率；
- 标准化模块接口，降低变更的连锁影响；
- 建立设计库、物料库和问题知识库。## 13. 常见迭代误区与案例

### 常见误区

- 不做根因分析，直接改板；
- 只改问题点，不评估关联影响；
- 跳过回归验证，导致新问题；
- 变更不升版本，文件与实物不一致；
- 新旧版本混用，导致现场混乱；
- 为降本牺牲可靠性和认证；
- 器件替换只看参数，不看软件和工艺；
- 认证变更未重新评估，导致合规风险；
- 迭代记录不完整，问题无法追溯。

### 典型案例

- 改一处、坏一片：修复接口问题时调整电源布局，影响 EMC，说明影响评估不完整；
- 降本导致批量失效：低价器件高温下参数漂移，说明替代验证不足；
- 新旧版本混用：客户现场两个版本软件配置不兼容，说明版本标识和切换管理缺失；
- 认证整改反复：整改后未做预测试，说明整改验证不充分。

## 14. 设计迭代的四个层次

1. 会改：能针对问题做出修改；
2. 会评：能评估变更的影响、风险和收益；
3. 会验：能设计合理验证范围和判定标准；
4. 会沉淀：能把问题转化为规范、清单和平台能力。

从“会改”到“会沉淀”，靠的不是加班改板，而是系统化迭代方法、严谨变更管理和持续知识沉淀。

迭代不是失败的证明，而是产品走向成熟的必经之路。

## 附录 A：设计迭代检查清单

### 触发与决策

- 问题现象、数据和影响范围清楚；
- 根因分析完成；
- 已评估是否必须改板及优先级；
- 迭代方案经过比较和评审。

### 变更管理

- 变更申请、影响评估和审批流程完整；
- 文件、物料和软件已同步；
- 版本号规则和追溯关系明确；
- 变更记录完整可查。

### 验证

- 变更项和回归验证范围明确；
- 新旧版本对比验证完成；
- 关键指标和安全项满足标准；
- 小批试产验证通过。

### 生产、供应链与客户

- 物料、交期和替代方案确认；
- 库存和在制品处理明确；
- 工艺文件和测试程序更新；
- 首件确认完成；
- 兼容性和切换影响已评估；
- 客户通知、备件和维修方案已落实。

### 认证与合规

- 变更对认证的影响已评估；
- 必要的重新测试或认证已完成；
- 认证文件和标识已更新；
- 合规风险已闭环。
